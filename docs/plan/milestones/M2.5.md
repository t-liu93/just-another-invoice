## Objective & Scope
- **Objective**: Consolidate scattered and semantically confused settings entry points into **a single gear icon in the top right → an Affine-style modal settings panel** (left sidebar categories, right-side in-place editing); keep business identity under a separate **Company icon**, with no overlap in responsibilities.
- **Current state (before refactor · already surveyed)**：`Dashboard.vue` / `Preferences.vue` / `SmtpSettings.vue` / `CompanyProfile.vue` each duplicate a header bar, entry points scattered as:
  - 🏢 `BusinessOutline` → `/settings/company` (company profile, acceptable)
  - 👤 `PersonOutline` → `/settings/preferences` (actually only theme; person icon ≠ preferences)
  - ⚙ `SettingsOutline` → `/settings/smtp` (gear icon only leads to SMTP, semantic mismatch)
  - ☀/🌙 Header direct theme toggle (duplicates Preferences page)
  - 🌐 Header direct language switch
- **Included (IN)**:
  - **Single gear entry + Affine-style modal panel** (see "Finalized Decisions"): left-side category navigation + right-side in-place editing.
  - **Category consolidation**: ① Preference (language + future defaults placeholder); ② Email SMTP (reuse existing endpoints); ③ Theme (consolidate scattered top-bar theme toggles); ④ AI (**placeholder only, disabled / "soon"**, no functionality).
  - **Header convergence**: top right only has **⚙ Gear (open panel) + 🏢 Company (→ company profile) + 🌐 Language shortcut + email tag + logout**; remove scattered 👤 person entry and independent ☀/🌙 theme toggle (theme moves to panel).
  - **Deduplication / reusability**: extract `AppHeader` for shared header bar, eliminate duplication across four views; refactor SMTP / theme forms into reusable content components for both panel and onboarding route shell.
- **Excluded (OUT)**:
  - **No new backend fields / endpoints** (red line: pure frontend; if contract alignment is truly needed, only regenerate `schema.d.ts`, milestone expected to produce zero changes).
  - **Business identity** (company name / logo / VAT / address / base currency / numbering rules) **does not enter gear panel** — stays at `/settings/company`, accessed via 🏢 Company icon.
  - Custom themes, multi-company switching, AI settings **specific functionality** (milestone only leaves AI category placeholder).
- **Corresponding documentation**: roadmap M2.5 cell + §2 red line 7 (rendering/input sanitization, no new input surface in this milestone).

## Finalized Decisions (locked before implementation · approved this round)

- [x] **Panel mounted on `App.vue`** (inside `n-config-provider` / message / dialog providers, parallel to `router-view`) — global overlay, stackable on any page; toggle uses a **module-level singleton composable `useSettingsPanel()`** (`open(category?)` / `close()` / `activeCategory`), same singleton pattern as `useTheme`.
- [x] **Category set**: `preference` / `smtp` / `theme` / `ai` (`ai` item disabled + "soon" label). Default panel entry stops at `preference`.
- [x] **Language dual entry**: top bar keeps 🌐 quick toggle (convenient) + panel "Preference" category includes language setting (canonical location) — matches author's selected mockup header. **Theme no longer in header**, only in panel "Theme" category.
- [x] **Route handling**:
  - `/settings/preferences`: **delete** (functionality merged into panel).
  - `/settings/smtp`: **keep** — onboarding flow depends on it (route guard allows `smtp-settings`, `Onboarding.vue` jumps to `?from=onboarding`); downgrade to **onboarding-only thin shell**, render extracted SMTP form component + "return to guide". Post-onboarding SMTP editing moves to panel.

- [x] **Reusability split**: extract `SmtpSettingsForm.vue` from `SmtpSettings.vue` (load/save/test logic + form body, no header); extract theme selection into panel's `ThemeSettings` fragment (reuse `useTheme`).
- [x] **Zero backend changes**: reuse M1/M2's `GET/PUT /settings/smtp`, `/settings/smtp/test`, `GET/PUT /settings/me`; don't touch `schema.d.ts` (should produce zero drift unless unexpected).

### Step 4 · Interface language account-level persistence (wrap-up follow-up)
> Wrap-up residual: in M2.5 body, language is session-level (panel/header 🌐 only sets `i18n.locale`, refresh returns to default `en`). This step makes it **account-level persistent**, aligning with theme (`useTheme`) behavior — both use USER-level `user.preferences`, load from server post-login, follow account across devices.
>
> **This is the only conscious small extension of M2.5's "zero backend" boundary** (add one field, no pricing, regenerate `schema.d.ts`); same nature as the SMTP radio follow-up that day.

- **Contract**: `schemas/setting.py` `UserPreferences` adds `locale: Literal["en", "zh"] = "en"` (consistent with current default). `GET/PUT /api/v1/settings/me` `response_model=UserPreferences` automatically includes the field, **endpoint logic unchanged**. After change, `npm run codegen` to regenerate `schema.d.ts`.
- **Backend task**: only add field to `UserPreferences`; no migration (values go into JSONB `value`, schema already dynamic dict).
- **Frontend task**: upgrade `composables/useLocale.ts` to `useTheme`-style singleton (`localStorage` cache + server-of-truth + `loadFromServer()` / `persistToServer()`); change language `n-select` in `PreferenceSettings.vue` and 🌐 in `AppHeader.vue` to use `useLocale.setLocale()` (write to DB + localStorage); load once post-login.
  - **Optimization point (determine at implementation time)**: `theme` and `locale` both in `/settings/me` — `useTheme.loadFromServer()` already `GET /settings/me`, let language **reuse same response** instead of extra request (can extract `loadUserPreferences()` to unify, both composables share).
- **Test**: backend `/settings/me` existing suite should remain green, add assertion "locale defaults to `en` + PUT round-trip shows value"; frontend `npm run build` green, `schema.d.ts` no drift.
- **Self-test point (add to acceptance below)**: switch language in panel/header → **persists after refresh** → switch browser/device, login same account → language follows.
