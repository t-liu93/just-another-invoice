## Goals & Scope
- **Goal**: A **register→login (forced MFA)→empty dashboard** private app; and land **email foundation + three-tier settings table structure** (password reset email flows, SMTP configurable on settings page).
- **IN (Included)**:
  - **Settings table foundation**: single table `setting` (key-value + `level` + `scope_id` + JSONB `value`), typed access + in-process cache; **M1 only accepts GLOBAL-layer read/write**, true `user→company→global` fallback and company/user layer semantics in M2.
  - **Authentication**: fastapi-users username (email)+password (**Argon2**); **httpOnly cookie session** (JWT strategy, signing secret self-managed: env override > auto-gen on first boot in DB); login/logout; `GET /users/me`; protected routes.
  - **Forced MFA (TOTP)**: mandatory on first login (no recovery codes); two-step login; CLI `jai reset-mfa` fallback.
  - **First account bootstrap**: first registrant becomes `owner`, after onboarding complete **disables public registration** (driven by `onboarding.completed` global flag).
  - **Email foundation**: SMTP send (`aiosmtplib` + `jinja2`), SMTP config stored in settings table (env fallback); **password reset email**; **SMTP settings page** (frontend fill & save + test email).
  - **Frontend**: register/onboarding, two-step login (with MFA setup wizard), logout, protected route guards + **empty dashboard**, forgot/reset password, SMTP settings, Pinia auth store; **dark mode** (Naive UI `darkTheme` + switcher + localStorage persistence + system preference default).
- **OUT (Not included / deferred)**:
  - Company business profile (name/logo/VAT/base currency/numbering) → **M2**; settings **company/user layer semantics completion, true `user→company→global` fallback + cache tuning** also in M2.
  - Invite-based multi-user, RBAC true auth (v1 owner has full power; user table here only **reserves** `company_id`/`role` columns).
  - RLS true implementation (M0's session hook stays empty).
  - Any business entities (invoices/customers/dictionaries…).
  - Passkey/WebAuthn, OAuth/SSO, API token, email read receipts.
- **Related docs**: analysis docs §3.3, §3.5, §3.6, §7.2.1; roadmap M1 / §1.1 / §2 (guardrails 2/5/7/11).

## Product Decisions to Fill In (define before starting; checked = decided, defaults tunable)
- [x] **First account bootstrap**: keep `/register` page; backend `registration_open = (user_count == 0)`, first registrant `role=owner`; separate global flag `onboarding.completed` (default `false`) drives frontend "should we still guide?". M1's onboarding = **register owner + bind MFA**, done → set `onboarding.completed=true` and permanently close public registration. Invite-based multi-user **deferred**.
  - > **M2 preview**: M2 will **insert "fill company profile" step** in onboarding (move completion point after profile filled), and can **optionally add "configure email (can skip)" optional step**; M1 only goes through MFA binding.
  - > **SMTP not in M1 forced onboarding**: SMTP config stays on **separate settings page** (step 4), can fill anytime; first boot doesn't force email to avoid friction. Password reset needs SMTP, but CLI fallback below means owner never locked out without email.
- [x] **Session credentials**: fastapi-users **CookieTransport + JWT strategy**. Token (JWT) in **httpOnly cookie**. **Signing secret resolution (`auth/secret.py`, resolved once at startup in lifespan)**: prefer `AUTH_SECRET` env explicit override; **if not set, auto-gen random on first boot and persist to settings table `GLOBAL/auth.secret`** (unique per deployment, zero-config self-hosted). Secret corruption/rotation only invalidates existing sessions, re-login recovers, no data loss. **No DB token table** (JWT stateless). `COOKIE_SECURE`: dev default `false` (uses `http://localhost`), prod default `true` (compose injects `${COOKIE_SECURE:-true}`; only returned on HTTPS, HTTPS terminated by Nginx reverse proxy; bare HTTP non-localhost deploy needs explicit `false`); `SameSite=lax`.
- [x] **MFA (TOTP)**: **Mandatory**, bind on first login; **no recovery codes**; recovery via CLI (see "CLI operations fallback" below).
- [x] **CLI operations fallback** (self-hosted premise: can touch server = have all permissions, password/MFA recoverable from CLI, **no email required**). Two modes: **dev mode** `uv run jai <cmd>` (project in venv); **deploy mode (in container)** `docker compose run --rm app jai <cmd>` (runtime image not pip-installed, provides `/usr/local/bin/jai` wrapper calling `python -m jai.cli`, no `uv`).
  - `jai reset-mfa <email>`: clear `totp_secret` + set `mfa_enabled=false`, next login requires re-binding MFA.
  - `jai set-password <email>`: reset password from CLI. **Owner never locked out even without SMTP**.
- [x] **Email library**: **`aiosmtplib` (async send) + Python built-in `email` (MIME construction) + `jinja2` (backend template, HTML auto-escape→guardrail 7, M9 PDF reuses same engine)**. SMTP config **fetched dynamically from settings table** (current config per send), env fallback. (No sync `smtplib`: blocks async loop; no `fastapi-mail`: config locked at startup, hard to fetch from DB dynamically.)
- [x] **TTL / time defaults** (tentative, changeable later): pre-auth (password passed, waiting MFA) cookie 5 mins; full session cookie 7 days; password reset token 1 hour.
- [x] **QR render location**: backend returns only `otpauth://` provisioning URI + base32 secret, **QR rendered by frontend** (frontend adds `qrcode` JS lib), backend no image dependency. Frontend **simultaneously shows copyable `otpauth://` URI and base32 secret** as fallback if QR doesn't scan.
- [x] **Dark mode**: added in M1 (frontend now used, pure white background too harsh). Implemented as **client theme**: Naive UI `darkTheme`/`lightTheme` + `n-config-provider` binding + switcher; preference stored **localStorage**, defaults **follow system** `prefers-color-scheme`. **Persist to account** (USER-level setting) deferred to M2 after settings layer completion.

## Contract (define first; backend and frontend each write against this)
> Business endpoints all `/api/v1/*`. Change contract → `npm run codegen` regenerate `schema.d.ts`, CI drift gate enforces no drift (guardrail 11).

**Bootstrap / Register (public)**
- `GET /api/v1/auth/bootstrap` → `200 {registration_open: bool, onboarding_completed: bool}` — drives frontend routes (decide whether to show register / login / continue guidance).
- `POST /api/v1/auth/register` body `{email, password}` → `201 UserRead`; **only if `registration_open` true**, else `403`. First registrant `role=owner`.

**Login (two-step · cookie)**
- `POST /api/v1/auth/login` body `{email, password}` → `200 {next: "mfa_setup" | "mfa_verify"}`, **set short-lived pre-auth cookie**; bad creds → `400`. (`mfa_setup` = user hasn't bound TOTP yet; `mfa_verify` = already bound, enter verification code.)
- `POST /api/v1/auth/mfa/setup` (needs pre-auth cookie) → `200 {secret, otpauth_uri}` — generate **pending-confirmation** TOTP secret.
- `POST /api/v1/auth/mfa/verify` (needs pre-auth cookie) body `{code}` → `204`; if valid: on first bind set `totp_secret`+`mfa_enabled=true`+set `onboarding.completed`, **upgrade pre-auth cookie to full session cookie**; bad code → `400`.
- `POST /api/v1/auth/logout` → `204`, clear session cookie.

**Password Reset (public)**
- `POST /api/v1/auth/forgot-password` body `{email}` → `202` (always return, prevent enumeration; if user exists and SMTP configured, send reset email).
- `POST /api/v1/auth/reset-password` body `{token, password}` → `204`; invalid/expired token → `400`.

**Current User (needs full session)**
- `GET /api/v1/users/me` → `200 UserRead {id, email, role, mfa_enabled, company_id}`.

**Settings · SMTP (owner, needs full session)**
- `GET /api/v1/settings/smtp` → `200 SmtpSettingsRead` (password field **redacted**, e.g. `password_set: bool`).
- `PUT /api/v1/settings/smtp` body `{host, port, username, password?, from_email, from_name?, use_tls, use_ssl}` → `200 SmtpSettingsRead`.
- `POST /api/v1/settings/smtp/test` → `202` (send test email to owner address using current config; fail → `400` with error).

## Data Models / Migrations
> M1 introduces **first real business tables** (M0 is empty baseline). Each table build = one Alembic migration.

- **`setting`** (single settings table, guardrail 5/6 foundation):
  - `id` UUID PK; `level` enum `GLOBAL|COMPANY|USER`; `scope_id` UUID **nullable** (GLOBAL null, COMPANY/USER point to respective entity, M1 doesn't use); `key` `text`; `value` **JSONB** (typed values); `created_at`/`updated_at`.
  - **Unique constraint** `(level, scope_id, key)`. M1 only reads/writes GLOBAL layer (`onboarding.completed`, `smtp.*`, `auth.secret`—where `auth.secret` is system-managed JWT signing key, never exposed via any API); COMPANY/USER layers just reserve structure for now. `scope_id` FK deferred to M2 when company/user tables land.
- **`user`** (fastapi-users UUID base table + reserved columns):
  - Base: `id` UUID, `email` (unique), `hashed_password`, `is_active`, `is_superuser`, `is_verified`.
  - **Reserved**: `company_id` UUID **nullable, no FK yet** (M2 adds FK + `ondelete` when `company` table lands, guardrails 2/3); `role` `text` default `'owner'` (RBAC later).
  - **MFA**: `totp_secret` `text` nullable, `mfa_enabled` bool default `false` (**add columns when creating user table together**, avoid second alter; M1 step 3 just uses them, no further table changes).
  - `created_at`/`updated_at`.
- **No token table** (JWT stateless, carries in cookie).
- **RLS**: M0's session hook stays empty; `setting`/`user` only **reserve** `scope_id`/`company_id`, RLS not activated this milestone.

## Atomic Steps Checklist
> Each step = one atomic change (single-person dev, no forced PR, CI green → merge to `main`), meets roadmap §5 DoD. ### Step 1 · Settings table + typed access + cache (foundation, do first)
- **Contract**: step doesn't expose new HTTP endpoints (SMTP read/write in step 4); only produces internal `services/settings`.
- **Backend**:
  - `models/setting.py`: `Setting` ORM (per data model); `models/_enums.py` add `SettingLevel`.
  - `schemas/setting.py`: internal typed value models (e.g. `OnboardingState`, later `SmtpSettings`).
  - `services/settings.py`: `get_setting(key, level, scope_id) -> typed` / `set_setting(...)`; **M1 requires GLOBAL-layer stable read/write + in-process cache** (invalidate on write). COMPANY/USER layers can stay placeholder or mock-overridden, true semantics in M2. Values parsed via Pydantic, **no `'YES'/'NO'` stringly-typed** (guardrail 5).
  - Alembic: create `setting` table (M1's first migration).
- **Frontend**: none (codegen unchanged).
- **Tests**: pytest—GLOBAL-layer read/write, cache hit/miss, typed parsing (bool/int/nested), unique constraint collision; if overriding fallback order, this step is mock/placeholder test only, not real company/user semantics acceptance.
- **DoD**: See roadmap §5.

### Step 2 · User model + password auth (cookie session) + registration gate
- **Contract**: `GET /auth/bootstrap`, `POST /auth/register` (gated), `POST /auth/login` (**this step single-step return full session, step 3 changes to two-step**), `POST /auth/logout`, `GET /users/me`.
  - > Note: this step login returns full session cookie directly after password; step 3 refactors to "password → pre-auth → MFA → full session". Both lands in M1, churn acceptable.
- **Backend**:
  - `models/user.py`: `User` (fastapi-users UUID base + `company_id`/`role`/`totp_secret`/`mfa_enabled` reserved columns).
  - `auth/`: fastapi-users setup—`UserManager`, **Argon2** password hashing (`pwdlib[argon2]`), `SQLAlchemyUserDatabase`, **CookieTransport + JWTStrategy** (signing secret resolved by `auth/secret.py`: env override > auto-gen DB `auth.secret`; `cookie_secure`/`SameSite`/TTL from config).
  - `api/auth.py`: mount fastapi-users register/auth routers to `/api/v1/auth`; `register` wraps onboarding gate (`registration_open` check + first registrant sets `role=owner`, **advisory lock serializes first registration**); `GET /auth/bootstrap`; `logout` public idempotent clears cookie.
  - `config.py`: add `AUTH_SECRET` (optional override), `COOKIE_SECURE` (dev `false`/prod `true`), session TTL (`session_ttl_days`/`pre_auth_ttl_minutes`). At startup `main.py` lifespan calls `resolve_auth_secret()` after migration check.
  - Alembic: create `user` table (with MFA columns).
  - **CLI entry**: create `jai` command script (`pyproject` `[project.scripts]`, dev mode `uv run jai`); runtime image places `/usr/local/bin/jai` wrapper (`python -m jai.cli`, deploy mode `docker compose run --rm app jai`). First subcommand `jai set-password <email>` (CLI password reset, no email needed → password recovery loop closes). `reset-mfa` reuses same entry in step 3.
- **Frontend**:
  - `stores/auth.ts` (Pinia): current user + login/logout actions (cookie auto-carried, `credentials: 'include'`).
  - `views/Register.vue` (gated by `bootstrap.registration_open`), `views/Login.vue` (password step), `views/Dashboard.vue` shell.
  - `router/`: protected route guards (unauthenticated → `/login`; `registration_open=false` → `/register` → `/login`).
  - **Dark mode**: `composables/useTheme.ts` (`darkTheme`/`lightTheme` switch + localStorage + system default); `App.vue` `n-config-provider` bound to theme; app shell has theme switcher.
  - `npm run codegen` regenerate `schema.d.ts`.
- **Tests**: pytest—registration gate (first succeeds+`owner`, second `403`), login sets cookie, `/users/me` unauthenticated `401`, logout clears cookie.
- **DoD**: See roadmap §5.

### Step 3 · Forced MFA (TOTP) + two-step login + CLI reset
- **Contract**: `login` returns `{next}` + sets pre-auth cookie; new `POST /auth/mfa/setup`, `POST /auth/mfa/verify`.
- **Backend**:
  - Depends on `pyotp`. `services/mfa.py`: generate secret, `otpauth_uri`, verify code (includes time window tolerance).
  - `auth/`: add **pre-auth strategy** (short-lived JWT, `scope=mfa` claim, only allows `mfa/*` endpoints); refactor `login` to two-step; `mfa/verify` on success upgrades to full session + on first bind sets `mfa_enabled`/`onboarding.completed`. **Users without bound MFA can't get full session** (enforced).
  - CLI: reuse step 2's `jai` entry, add `jai reset-mfa <email>` (clear `totp_secret` + set `mfa_enabled=false`).
- **Frontend**:
  - `Login.vue` extended: after password step, check `next` to enter **MFA setup wizard** (`qrcode` JS renders `otpauth_uri` + **same screen shows copyable otpauth URI and base32 secret** as manual-entry fallback + code confirmation) or **MFA verify step** (already bound, enter code).
  - Setup success → dashboard.
- **Tests**: pytest—TOTP validation (valid/invalid/adjacent time window), two-step login (no MFA can't get full session), `reset-mfa` clears then requires rebind; frontend basic form validation.
- **DoD**: See roadmap §5; **MFA/TOTP validation logic must have unit tests**.

### Step 4 · Email/SMTP foundation + password reset + SMTP settings page
- **Contract**: `POST /auth/forgot-password`, `POST /auth/reset-password`, `GET/PUT /settings/smtp`, `POST /settings/smtp/test`.
- **Backend**:
  - `services/email.py`: `aiosmtplib` send + `jinja2` template; **SMTP config fetched dynamically from `services/settings`** (env fallback); **autoescape before rendering user input** (guardrail 7).
  - `schemas/setting.py`: `SmtpSettings` (typed); password **redacted** on read.
  - `api/settings.py`: `GET/PUT /settings/smtp` (owner only) + `POST /settings/smtp/test`.
  - `api/auth.py`: mount fastapi-users `forgot/reset` routers, reset token email sent via `services/email`; `forgot-password` always returns `202` (prevent enumeration).
  - Reset email Jinja template (EN/ZH placeholders).
- **Frontend**:
  - `views/settings/SmtpSettings.vue`: fill & save SMTP + "send test email" button.
  - `views/ForgotPassword.vue` + `views/ResetPassword.vue` (landing pages with token link).
  - i18n: add text to `en.json`/`zh.json`.
- **Tests**: pytest—reset token generation/validation/expiry; email construction (mock SMTP, assert recipient/subject/body escaped); SMTP read/write redaction; `forgot-password` returns `202` even for nonexistent email.
- **DoD**: See roadmap §5.
