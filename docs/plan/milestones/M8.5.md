> **Rationale**: After M8's final manual walkthrough, author compared each column of their Dutch sole trader Excel against the system's `Expense` entity and found three accounting dimensions **not currently modeled**: **payment source (private/business account)**, **business-use percentage**, **depreciation years**. ## Goals and Scope
- **Goal**: Add three **pure storage** fields to `expense` (and `recurring_expense` template for parity) — payment source, business-use %, depreciation years — so the data model reflects author's Dutch Excel; editor/list can capture and display; EN/ZH complete. **No new money-math logic.**
- **Dependencies / Position**: Additive extension over **M8** expense line (no changes to existing money-math / split / snapshots / receipts / recurrence logic); placed **after M8, before M9**.
- **In Scope**:
  - `models/_enums.py`: Add `PaidBy(StrEnum) { PRIVATE, BUSINESS }`.
  - `expense` + `recurring_expense` each add three columns: `paid_by` (Text, NOT NULL, server_default `'BUSINESS'`), `business_percentage` (`NUMERIC(6,3)`, NOT NULL, server_default `'100'`), `depreciation_years` (Integer, NOT NULL, server_default `'1'`). **One additive migration** (0021); NOT NULL + server_default auto-backfill existing rows.
  - `schemas/expense.py` + `schemas/recurring_expense.py`: `ExpenseInput`/`ExpenseRead`/`ExpenseListItem` and `RecurringExpenseInput`/`RecurringExpenseRead` each add three fields (with range validation).
  - `services/expense.py` + `services/recurring_expense.py`: CRUD persists three fields (pure storage, no calculation); when generating recurring drafts, **copy** these three fields to generated `Expense`.
  - Frontend: expense editor (Paid By radio / Business % / Depreciation years three controls), expense list (readable display), recurring editor parity (secondary), i18n EN/ZH; **contract changed → `npm run codegen` regenerate `schema.d.ts`** (red line 11).
- **Out of Scope / Deferred**:
  - **Actual yearly Expense / refundable VAT by year / quarterly aggregation / BTW box mapping** → **M10** (depends on "which year to report"; M8.5 only **stores fields correctly**).
  - **Any derived amount calculation or display** (including `net × business%` kind of "deductible base reference") → **Not doing** (author explicit: M8.5 store-only, see D1).
  - **Cross-year depreciation amortization schedule / mid-year convention for depreciation start** → M10; M8.5 depreciation start date directly uses `expense_date`; mid-year convention added later if needed.
  - **Multi-line grouping entity / shared attachments** → Not doing (one row per item, each uploads same PDF; existing model supports this; see D7).
  - **New business endpoints / modify AI pipeline / modify receipt storage** → Not doing (reuse M8's existing CRUD and contract; only expand fields).
  - **Change column type / alter existing table structure** → No (pure add columns).
- **Corresponding Docs**: roadmap M8.5 / §2 red lines 1 (no new money-math) / 10 (text) / 11 (codegen) / 12 (VAT data-driven; unchanged); `milestones/M8.md` (expense baseline).

## Frozen Decisions (D1–D9 · Decided with author 2026-06-14)
- [x] **D1 · Three new fields "pure storage, no calculation"**: `paid_by` / `business_percentage` / `depreciation_years` only persist; no backend calculation participation. M8.5 **adds no money-math** — `gross = net + vat` is M8's existing logic; red line 1 "calculate in services" adds **no new money math here**. All derivatives (Actual Expense, refundable VAT by year, quarterly, BTW) deferred to M10.
- [x] **D2 · `paid_by` = enum `PRIVATE | BUSINESS`, pure indicator**: Marks whether paid from private account or company account (author often uses private account for convenience; files tax return as "private capital injection"). **No calculation involvement**. Store as Text + `PaidBy` StrEnum (house style: enums stored as Text column, same as `frequency` / `vat_treatment_effect`); default `BUSINESS`.
- [x] **D3 · `business_percentage`**: `Decimal` 0–100, default 100, column `NUMERIC(6,3)` (reuse `_RATE` precision). M8.5 storage only; M10 uses it to **simultaneously reduce refundable VAT and expenses** (Dutch: business assets with private use → both deduction and expense by this %).
- [x] **D4 · `depreciation_years`**: `int` ≥1, default 1. `=1` full year expensed (normal expense); `>1` treat as large asset depreciation, amortize yearly — **amortization algorithm (including "is VAT also amortized yearly?") entirely in M10**. Depreciation start date uses `expense_date`. Author: assets >€449/~€500 require depreciation (commonly 5 years; also 2/10 year); **threshold not enforced in M8.5** — user fills years (=1 means not depreciated).
- [x] **D5 · `deductible` semantic unchanged = "can refund VAT"** (author's VAT Refundable column): No separate "P&L deductible" second boolean. Expenses default as business cost in P&L; private-use portion reduced by `business_percentage` in M10; personal invoice no-VAT refund situations handled by input method (see D6), not a new field.
- [x] **D6 · Personal invoice business-use not newly modeled**: Invoice to individual but business purpose, VAT non-refundable; author's input method = **`net_amount` filled with gross, `vat_amount` changed to 0** (VAT already overridable input, landed in M8 walkthrough). So "Actual Expense" two cases (company invoice = net÷years; personal invoice = gross÷years) **merge into one** `net × business% ÷ depreciation_years` (M10 calc); M8.5 needs no extra field.
- [x] **D7 · Multi-line per invoice = one row per item + each uploads same PDF**: Current "one Expense = one row + attachment attached" already supports (author's Excel: same invoice filename appears multiple times). **No grouping entity, no shared attachments.** **Multi-item only manual entry** — AI reads one image at a time, doesn't know which item; best-effort prefill supplier/date etc.; M8.5 **doesn't modify AI pipeline / attachments**.
- [x] **D8 · `recurring_expense` template parity**: Add same three columns; when generating recurring draft, **copy** into generated `Expense`; maintain M8's existing field symmetry between expense ↔ recurring (blind review checks this). Recurring **UI secondary** (author doesn't use periodic expenses now), but schema/service must match.
- [x] **D9 · No new business endpoints, contract only expands fields**: Reuse existing `POST/PUT /expenses`, `/recurring-expenses` etc. endpoints; only add fields to `ExpenseInput/Read/ListItem` and `Recurring*`. Contract changed → `npm run codegen` regenerate `schema.d.ts`, CI drift gate enforces no drift (red line 11). No AI / receipt / money-math endpoint changes.

## Note (Not a Decision · For M10 Reconciliation)
- Author stated "large depreciated assets **also amortize VAT yearly**" (e.g., VAT 1000, 5 years → refund only 200/year). Dutch standard: **input VAT refunded in full in purchase quarter**, VAT amortization only appears in *herzieningsregeling* (capital assets / real estate, when use-% changes across years). **M8.5 unaffected** (just stores `depreciation_years`); when **M10** BTW reporting, whether "VAT also amortizes yearly" must re-verify against Dutch Tax Authority (Belastingdienst) — directly affects each quarter's BTW box numbers.

## Money & Storage Rules (M8.5 Frozen · No New Calculations)
> Red line 1: Calculate only in `services`. This milestone **adds no money-math** — three fields pure storage, no derivatives.

- `paid_by`: Store as-is (validated `PaidBy` enum value); no calculation.
- `business_percentage`: Store as-is (`Decimal`, 0 ≤ x ≤ 100); **M8.5 doesn't multiply any amounts**.
- `depreciation_years`: Store as-is (`int` ≥ 1); **M8.5 does no amortization**.
- Existing `net / vat / gross / base_* / deductible / snapshot / single-currency` ledger **completely unchanged** (M8 frozen).
