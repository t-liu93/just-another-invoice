> **缘起**：M7 收款人工 walkthrough 发现真实发票 `F2026-009` 永远收不满——含税总额存为 3 位 `3865.166`，UI `toFixed(2)` 显示 `3865.17`，而收款只能按「分」（2 位）走：付 `3865.17`（量化 `3865.170`）> `3865.166` → 触发超额守卫；付 `3865.16` 余 `0.006`（显示 `0.01`），补 `0.01` 又超额。**根因不是浮点误差，而是 M5 定价引擎把「应付总额」也只量化到 3 位、从未落到货币最小单位（分）**，导致「显示 = 应付 = 对账」三者口径不一致。

## 目标与范围
- **目标**：让**面向客户 / 对账 / 申报的货币量**统一落到**货币最小单位（v1 = EUR = 2 位 / 分）**，使「前端显示 = 应付额 = 后端对账 = 供应商发票 / 银行流水」自洽；同时**保留 `unit_price` 的 ≥3 位输入精度**（按 kWh/Wp 等单价计价的大件需要）。
- **纳入（IN）**：
  - `services/money.py`：加 `quantize_to_minor_unit`（最小单位量化，EUR=2，`ROUND_HALF_UP`），与既有 `quantize_money`（3 位中间精度）分工明确。
  - `services/pricing.py`：**行级到分**口径（见下「算钱口径」），覆盖 LINE / DOCUMENT 两模式 + 含税 / 不含税两方向。
  - `services/invoice.py` / `services/quote.py` **持久化层**：把文档级 + 行级快照的量化从 `quantize_money`(3 位) → `quantize_to_minor_unit`(分)，杜绝某字段悄悄停在 3 位；`unit_price` / `quantity` **不动**。
  - 回归测试 + **新增「3 位总额可按分收满」端到端用例**。
- **不纳入（OUT / 顺延）**：
  - **历史数据重算 / 迁移脚本** → **不做**。项目未上线、库里全是测试模拟数据、无真实生产数据；旧的 3 位测试发票（含卡住的 `F2026-009`）**删了重建**即可。引擎修正后只保证「**新算的**单据到分」。
  - **`services/costing.py`（M6.5 估算引擎）零改动**：估算表是**纯内部**工作表（成本 / 利润 / 时薪，客户看不到）；其每组卖价 `group_sell_excl_vat`（3 位）在 `generate_quote_from_estimate` 里是**当作报价行 `unit_price`（输入）**塞进去的，报价走 M5 引擎、由本里程碑的行级到分**自动修对**。`total_incl_vat_indicative` 本就是 informational / 不持久化的内部参考数，留 3 位无妨。
  - **`services/payment.py` 零改动**：`recompute_payment_state` 的 `due = total − paid` 与超额守卫 `paid_total > total`，在 `total` 落到分后**自然成立**；其对 `paid/due` 的 3 位归一化对「分」值**幂等**。
  - **M8 expense**：开支落地时按**同一行级到分口径**（输入本就是供应商发票分值），属 M8 范围，本里程碑只留注记。
  - **多币种最小单位字典**：v1 仅 EUR=2 硬编码 + 留口子（`minor_unit` 参数）；多币种顺延。
  - **整欧元报价**：是**输入端**选择（加一笔 discount），不写进算钱引擎（D4）。
  - **改列类型 / 改 schema / 改 API 契约**：均无（D5）。`NUMERIC(18,3)` 容得下 2 位（第 3 位恒 0）；无契约改动 ⇒ **无需 `npm run codegen`**。
- **对应文档**：roadmap M7.5 / §2 红线 1；分析文档 §2.5；M5 `services/pricing.py`、`services/money.py`。

## 已冻结决策（D1–D7 · 作者共定 2026-06-13，含本轮细化）
- **D1 · 舍入粒度 = 行级到分**（方案 B 伞下的子粒度，作者拍板）：每行先把 `数量 × unit_price` **乘完再落到分**，逐行 `net / VAT / total` 全部到分；**单据 = 各行（已是分）相加**，不二次舍入。按税率组汇总（M10 BTW）= 同税率各行分值相加，**天然自洽**；多行同率**不做组级 VAT 分摊**（行级各自到分即可）。`F2026-009` 形态 → `3194.35 / 670.81 / **3865.16**`。
  - 与原口述（「行保 3 位、仅最终总额到分」→ `3865.17`）相比改为**行级**。理由：作者真实场景 `net` 本就到分（供应商发票照抄、自定价从 Estimate 出来即「分」相加），3 位仅偶发计算残渣；行级一把约掉最干脆、**免余数分摊**；且每税率组 `net + VAT = total` 在**行 / 组 / 单据三级**都自洽，直接对齐 M10 BTW 按格子申报（见记忆 [[vat-model-two-axis]]）。
- **D2 · 适用范围 = 全部「文档级」货币出参**：发票 `total_incl_vat` / `due_amount` / 每行·每税率组 `taxable`·`vat` + 对应 `base_*`；报价同构；估算对客面经报价引擎自动到分（见 OUT 之 costing）。
- **D3（修订）· 精度边界**：**唯 `unit_price` 保留 ≥3 位**（输入精度）；`数量 × unit_price` **乘完之后落到分**，逐行 `net / 折扣 / VAT / total` 全部到分。
  - 安全性：**先乘后舍**、`unit_price` 不动 ⇒ 不会发生「单价被提前砍 2 位 × 大数量」累计误差（这正是 D3 原意要防的）。
  - 注：D3 原文把「行小计 / 折扣 / 逐行中间量」也列为 ≥3 位；本轮按行级到分**修订为仅 `unit_price` 维持 ≥3 位**。
- **D4 · 不舍到整欧元**：VAT 必须按分算与申报，引擎坚持到分；要整数报价是**输入端**加 discount 的事，不进引擎。
- **D5 · 不改列类型 / 不改 schema / 不改契约**：`NUMERIC(18,3)` 容得下 2 位；无 Alembic、无 codegen。
- **D6 · `currency_minor_unit` 概念**：v1 EUR 硬编码 = 2，`quantize_to_minor_unit(value, minor_unit=2)` 留口子（未来某些币种 3/0 位）；与 `quantize_money`（3 位中间）分工明确。
- **D7（修订）· 无历史重算**：项目未上线、无生产数据 ⇒ 不做迁移脚本；旧测试数据重建。
- **舍入方向 · 跟随 `amounts_include_vat`**：净额录入（B2B，多数）→ 行 `net` 为锚先到分、`VAT/gross` 派生；含税录入（B2C 整价）→ 行 `gross` 为锚先到分、`net/VAT` 派生。

## 算钱口径（钉死 · `services/pricing.py` + `services/money.py`）
> 红线 1：算钱只在 `services`；schema 不算钱。**引擎是唯一权威**，持久化层只**跟随其分值**落库、不在别处以**不同标度**二次量化。

**最小单位量化工具（`money.py`）**
- `MINOR_UNIT = 2`（EUR）；`MINOR_QUANT = Decimal("0.01")`；复用 `MONEY_ROUNDING = ROUND_HALF_UP`。
- `quantize_to_minor_unit(value: Decimal, minor_unit: int = 2) -> Decimal`：按 `10^-minor_unit` 量化、`ROUND_HALF_UP`。`minor_unit=0` 退化为整数量化（留口子，本里程碑不用）。
- 与 `quantize_money`（3 位）**并存**，职责分明：3 位 = 中间计算；2 位 = 文档级 / 行级对客终值。

**逐行（`pricing.py`，方向随 `amounts_include_vat`）**
- `unit_price`：≥3 位，**不动**。
- 行小计 = `quantize_to_minor_unit(数量 × unit_price)`（**先乘后舍**）。
- 行折扣额、整单折扣按行分摊额：**到分**（`_calc_discount_amount` / `_distribute_fixed_discount` 改用最小单位量化；后者「最后一行兜余数」保持 `Σ 分摊 = 折扣总额`——这是**折扣额**分摊，与 VAT 无关，本就存在、继续保留）。
- **不含税录入**：`net分 = 小计 − 折扣`（已到分）；`VAT = quantize_to_minor_unit(net分 × 有效税率 / 100)`；`行总额 = net分 + VAT`。
- **含税录入**：`gross分 = 小计 − 折扣`（已到分）；`net = quantize_to_minor_unit(gross分 / (1 + 率/100))`；`VAT = gross分 − net`。
- **LINE 模式**：逐行如上，`InvoiceLineTax` 存逐行（已是分）`net / VAT`。**DOCUMENT 模式**：行小计到分、单据级单一税率组按上式到分（`doc_taxable / doc_vat / doc_total` 到分），`InvoiceTax` 存该组分值。

**汇总（= 各行 / 各组分值直接相加，不二次舍入）**
- `subtotal_excl_vat / taxable_amount / vat_total / total_incl_vat` = Σ 行分值；`due_amount` 初始化 = `total_incl_vat`（分）。
- `base_*` = 对应 `*`（v1 单一本位币 EUR、`exchange_rate = 1`）。

**不变量（测试必须断言）**
- 每行：`net + VAT = total`（分级）。
- 每税率组（同税率各行汇总）：`Σnet + ΣVAT = Σtotal`，且各为分。
- 单据：`taxable + vat = total`（分级）；`Σ按税率组 = 单据`。
- **可收满**：`total` 为分 ⇒ 按分逐笔可收到 `due = 0` 且 `COMPLETED`（接 M7，payment 零改动）。

### 步骤 1 · `money.py` 加最小单位量化
- **后端**：加 `MINOR_UNIT` / `MINOR_QUANT` + `quantize_to_minor_unit(value, minor_unit=2)`（`ROUND_HALF_UP`）；docstring 写清与 `quantize_money` 的分工（3 位中间 vs 2 位对客终值）。
- **测试**（纯函数）：半分边界（`1.005 → 1.01` 进位、`1.004 → 1.00` 舍去）、负数（`-1.005 → -1.01`）、`minor_unit=0` 退化整数、`minor_unit=2` 常规、**幂等**（量化已是分的值不变）。
  - ⚠️ 不要在这步断言「`3865.166 → 3865.17`」当作里程碑目标——那只是该函数对单个数的 2 位量化（口径 B/`.17`）；本里程碑的 `F2026-009 → 3865.16` 是**引擎行级到分**的结果，断言放步骤 2/3。
- **盲审要点**：① `ROUND_HALF_UP` 与 `quantize_money` 一致；② **不改** `quantize_money` 行为；③ `minor_unit` 参数化但默认 2、EUR 硬编码处集中（D6 口子）。

### 步骤 2 · `pricing.py` 行级到分 + 持久化层标度对齐
- **后端**：
  - `pricing.py`：按上「算钱口径」把逐行 `net / 折扣 / VAT / total` 改为 `quantize_to_minor_unit`；覆盖 **LINE / DOCUMENT** 两模式 + **含税 / 不含税**两方向；`_calc_discount_amount` / `_distribute_fixed_discount` 改最小单位量化（保持「最后一行兜余数」）。**汇总仍为各行分值相加、不二次舍入**。
  - `invoice.py` / `quote.py` **持久化层**：把文档级 + 行级快照的 `quantize_money(...)` 调用改为 `quantize_to_minor_unit(...)`（`invoice.py` 现约 line 427–441 文档级、543–551 行级，以及 quote→invoice 转换路径）；`unit_price` / `quantity` **复制不动**；`due_amount` 初始 = 分级 `total`。
- **测试**（算钱必测，红线 1）：更新现有 pricing 单测期望值到分；**新增不变量断言**（行 / 组 / 单据三级 `net + VAT = total`、`Σ组 = 单据`）；**单行高价**（`unit_price` 3 位 → 行到分，`F2026-009` 形态断言 `3194.35 / 670.81 / 3865.16`）；**多行同率**（各行到分相加、无组级分摊）；**多税率**（每组自洽）；**含税录入**方向；整单 fixed 折扣分摊到分且 `Σ = 折扣额`。
- **盲审要点**：① 所有文档级 / 行级出参是否都到分、`unit_price` 是否仍 ≥3 位（D3 修订）；② 方向是否真随 `amounts_include_vat`（**两条路径都改**）；③ 持久化层**无任何字段悄悄停在 3 位**（grep `quantize_money` 残留确认）；④ 折扣「最后一行兜余数」在分级仍 `Σ` 自洽；⑤ DOCUMENT 模式 placeholder / 单组路径一致到分；⑥ `base_*` 跟随。

### 步骤 3 · 回归 + 收满闭环
- **测试**：跑**全量后端测试**（M5/M6/M6.5/M7 既有算钱与收款集成）绿；**新增端到端回归**：建一张 `F2026-009` 形态发票（单行 `unit_price = 3194.352`、21%、`SENT`）→ 断言 `total = 3865.16` → 按分录一笔 `3865.16` → `due = 0`、`paid_status = PAID`、`status = COMPLETED`（验证 M7 收款层**无需改动即自洽**）。
- **盲审要点**：① 是否真覆盖「3 位总额历史 bug」的回归（**这条是本里程碑存在的理由**）；② 既有测试期望值更新是「口径修正」而非「迁就实现」（核对几条手算）；③ payment 测试无改动仍绿（佐证「零改动」结论）。
