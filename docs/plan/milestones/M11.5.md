## Dependencies and existing capabilities

- **M6 Quote**: quote CRUD, `ACCEPTED` status, and row-locked atomic quote→DRAFT-invoice conversion.
- **M7 Payment**: multiple/partial invoice payments, payment-method snapshots, and the `due_amount`/`paid_status`/`COMPLETED` state engine.
- **M7.5 money rules**: customer-facing money rounds to the currency minor unit; internal arithmetic uses `Decimal`.
- **M9 PDF**: invoice/quote/payment-receipt PDF plus email attachments.
- **M10 BTW**: output VAT currently reads `SENT`/`COMPLETED` invoices and groups by `invoice_date`.
- **Legal anchor**: when all or part of the consideration is received, VAT for that portion arises no later than receipt; see [Wet OB 1968 Article 13(2)](https://wetten.overheid.nl/BWBR0002629/#HoofdstukII_Afdeling4_Artikel13).

## Goal and scope

**Goal**: Before the final invoice exists, allow deposits on an accepted quote; transfer them automatically to the final invoice; give the customer one formal invoice showing the complete project price and VAT; internally recognise VAT by payment date without duplicate filing.

Included:

- Multiple payments on an `ACCEPTED` quote.
- Per-payment VAT snapshots with proportional mixed-rate allocation.
- Automatic quote→invoice attachment while permanently retaining quote provenance.
- Recomputed paid, due and status state after conversion.
- Final invoice/PDF showing every payment, total paid and amount due.
- Quote-stage receipt explicitly marked as not a VAT invoice.
- Positive advance recognition and final-invoice offset in BTW reports.
- A global payment list supporting quote-origin and invoice-origin payments.

Excluded:

- Formal advance/instalment invoices.
- Standalone or unallocated customer credit.
- Refunds, negative payments or overpayment.
- Reassignment to an unrelated invoice.
- Percentage-based deposit calculators.
- EU B2B/B2C, reverse-charge or export advance handling.
- Historical VAT-snapshot backfills for existing invoice payments.

## Frozen product and architecture decisions

- [x] **D1 · One final VAT invoice**: quote-stage payments/receipts consume no invoice number.
- [x] **D2 · VAT by payment date**: when the final invoice is issued, previously recognised quote-payment VAT is offset from the current BTW period.
- [x] **D3 · Accepted quotes only**: payments never change quote status automatically.
- [x] **D4 · Automatic transfer**: conversion sets `payment.invoice_id` and permanently preserves `payment.quote_id` in the same transaction.
- [x] **D5 · Invoice manages transferred payments**: the quote retains read-only provenance; edit/delete moves to the invoice.
- [x] **D6 · `NL_DOMESTIC` only**: every other VAT treatment receives an explicit `422`.
- [x] **D7 · Whole-document proportional allocation**: the frontend never selects a tax line or supplies VAT.
- [x] **D8 · No overpayment**: cumulative quote/final-invoice payments cannot exceed gross total.
- [x] **D9 · Final invoice remains editable**: customer, currency, paid coverage, VAT buckets and date must satisfy safety guards.
- [x] **D10 · Quote receipt is not a VAT invoice**: after final locale resolution its PDF carries an explicit single-language warning.
- [x] **D11 · Final invoice lists every payment**: date, reference, amount, paid total and remaining amount.
- [x] **D12 · No early P/L revenue**: advances affect cash and BTW timing only; revenue begins with the formal invoice.
- [x] **D13 · Payments remain editable/deletable**: mutations recompute tax snapshots and dynamic historical reports; the user decides whether a filed period needs correction.
- [x] **D14 · Deleting a converted DRAFT does not delete payments**: they return automatically to the quote, which can be converted again.
- [x] **D15 · A paid DRAFT cannot be cancelled directly**: delete the draft to return payments or handle the payments first.

## Locked API contract

All contract changes regenerate and commit `frontend/src/api/schema.d.ts`.

### Quote payment API

- `POST /api/v1/quotes/{quote_id}/payments` accepts existing `PaymentInput` and returns `201 QuotePaymentsResponse`; requires `ACCEPTED`, `NL_DOMESTIC` and unconverted.
- `GET /api/v1/quotes/{quote_id}/payments` returns `200 QuotePaymentsResponse`; remains readable after conversion, with a read-only frontend.

### Existing payment API changes

- `GET /api/v1/payments/{payment_id}` returns extended `PaymentRead`.
- `PUT` and `DELETE /api/v1/payments/{payment_id}` return `PaymentMutationResponse` (`deleted=false/true`).
- `GET /api/v1/payments` searches invoice number, quote number and customer name. Transferred rows navigate to invoice; untransferred rows navigate to quote.

### Core schemas

- `PaymentTaxRead`: optional `vat_rate_id`; rate label/percent; taxable, VAT and gross amounts; matching `base_*` amounts.
- `PaymentRead`: existing fields plus `origin_type: "INVOICE" | "QUOTE"`; nullable invoice/quote IDs and numbers; `tax_breakdown: PaymentTaxRead[]`.
- `QuotePaymentsResponse`: quote ID/number, optional converted invoice ID, gross total, paid total, remaining amount and items.
- `PaymentMutationResponse`: payment ID, deleted flag, optional quote aggregate and optional invoice aggregate.
- `PaymentListItem`: nullable invoice/quote IDs and numbers, origin type, customer, payment date, amount, method and creation time.

## Data model and migration

### `payment`

- Make `invoice_id` nullable and change its FK from `ON DELETE CASCADE` to `ON DELETE SET NULL`.
- Add nullable, indexed `quote_id` FK to `quote.id` with `ON DELETE RESTRICT`.
- Add `CHECK (invoice_id IS NOT NULL OR quote_id IS NOT NULL)`.
- `quote_id != NULL` means quote-origin even after conversion; `quote_id == NULL && invoice_id != NULL` means legacy invoice-origin.
- Existing rows remain invoice-only without recalculating values, states, times or historical reports.

### `payment_tax`

Each quote-origin payment stores one row per aggregated VAT bucket: ID, payment FK (`ON DELETE CASCADE`), nullable VAT-rate FK (`ON DELETE SET NULL`), rate label/percent snapshot, VAT treatment code/effect/requires-ICP snapshot, taxable/VAT/gross and matching base amounts, a stable bucket key and sort key. Money is `NUMERIC`; text snapshots use `text`. ORM and DB cascades manage children. The migration follows the current linear head and does not backfill historical payments.

## Money and state rules

### Quote payments

1. The quote must be frozen in `ACCEPTED`.
2. The service normalises payment amount to the currency minor unit.
3. `paid_total = Σ quote-origin payment.amount`.
4. `remaining_amount = quote.total_incl_vat − paid_total`.
5. A cumulative amount above quote total returns `422`.
6. Quote paid status is derived in the aggregate response, never persisted.

### Mixed-rate allocation

1. Aggregate VAT buckets from the quote's persisted document/line tax snapshots.
2. Split every bucket into remaining taxable and VAT components.
3. Stable payment order is payment date, creation time and ID.
4. Allocate each payment proportionally across remaining components.
5. Use integer minor units and deterministic largest remainder so each payment satisfies taxable+VAT=gross, every allocation is non-negative, full payment exactly matches quote tax snapshots, and no cent drifts.
6. Editing/deleting a quote-origin payment recomputes every payment-tax row for that quote in one transaction.
7. The allocator is a DB-free pure function with dedicated unit tests.

### Quote→invoice conversion

1. Continue locking the quote `FOR UPDATE`.
2. Create the DRAFT invoice and copy amount/tax snapshots.
3. Lock and load quote payments.
4. Set their `invoice_id`, retaining `quote_id`.
5. Reuse the payment state engine to compute due/base due/paid status.
6. Lifecycle remains `DRAFT` even if fully paid.
7. Set `converted_invoice_id` and commit once; any failure rolls back everything.

### Invoice editing and status

- For a DRAFT with quote-origin payments: customer/currency cannot change; invoice date cannot precede any payment date; total cannot fall below paid total; no final VAT bucket may fall below the already recognised taxable/VAT snapshot.
- DRAFT→SENT yields `SENT + PARTIALLY_PAID` when partial, and directly `COMPLETED + PAID` when fully paid.
- Deleting the DRAFT lets DB FKs set payment `invoice_id` and quote `converted_invoice_id` to null, leaving payment linked by quote.
- DRAFT→CANCELLED with payments returns `422`.

### Concurrency

- Add/edit/delete and quote conversion lock the same parents.
- Lock order is quote first then invoice for quote-origin; invoice only for invoice-origin.
- Concurrent payments cannot jointly overpay; payment/conversion races resolve with either the payment included in conversion or conversion winning and the new quote payment failing.

## BTW reporting

- Quote-origin payment tax in the report period is added by `payment_date`.
- A final invoice is first added in full under existing rules, then all quote-origin payment tax attached to it is subtracted, irrespective of the advance quarter.
- Same-quarter advance+invoice cancels the advance/offset and leaves the full invoice VAT in that quarter. Cross-quarter processing recognises deposits earlier and only the remainder in the final quarter. All quarters sum to the complete invoice VAT.
- P/L, dashboard revenue and ICP remain invoice-based and never read payment tax.
