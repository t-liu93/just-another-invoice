## Goals and Scope
- **Goal**: Record one or multiple payments (first/mid/final installment) for one issued invoice, backend authoritatively recalculates amount owed and payment status, auto advance lifecycle to `COMPLETED` when fully paid; payment records support edit/delete with immediate recalculation (can revert to `PARTIALLY_PAID` and `COMPLETED` back to `SENT`). **All calculations in backend, single base currency**.
- **IN**:
  - **Payment entity (invoice child record)**: `payment` (has `company_id` + `invoice_id`, cascade to invoice). Record `payment_date` / `amount` / payment method snapshot / note.
  - **`services/payment` recalculation engine (tax-agnostic, pure state/amount)**: `recompute_invoice_payment_state(invoice)`—by accumulating that invoice's all payment `amount`, recalculate `due_amount`/`base_due_amount`/`paid_status`/`status`; `Decimal`, **sum of already-rounded per-payment amount, no second rounding** (same as M5/M6.5). **Costing/state logic must be unit-tested** (red line 1).
  - **Lifecycle linkage (decision D3, author fixed)**: `paid_status == PAID` ⇒ `status = COMPLETED`; payment edited smaller/deleted causing not fully paid ⇒ `COMPLETED` revert `SENT`. **Only engine-driven**, don't use manual `transition_status` (latter still rejects manual COMPLETED with `422`).
  - **Payment mutability (decision D4, author fixed)**: payment can `PUT`/`DELETE`, each time recalculate. No reversal entries.
  - **Guards**: ① precondition—record/edit payment requires invoice `status ∈ {SENT, COMPLETED}` (issued), record payment on `DRAFT`/`CANCELLED` → `422`. ② overage—if operation makes accumulated payment > invoice total incl vat → `422` (`due_amount` can't go negative; credit/refund deferred).
  - **Payment method**: `payment_method_id` select from M4 dictionary; on persist **snapshot** `payment_method_name` (delete dict item don't break history, FK `SET NULL`).
  - **Overview**: `GET /payments` global list (filter by customer / method / date range + pagination), supply "payments" overview page.
  - **Frontend**: Invoice detail page **payment panel** (list that invoice's payments + add/edit/delete + real-time `due_amount`/`paid_status` badge); top-level "Payments / Payments" overview page (reuse above global list).
- **OUT / defer to later**:
  - **Standalone / unallocated payment (not linked to invoice)** → don't do. `invoice_id` in v1 **NOT NULL** (each payment belongs to one invoice). roadmap mentions "associate invoice / standalone", standalone defer to future additive (add nullable column, old data untouched).
  - **Overage / credit balance / refund (negative payment)** → don't do (overage directly `422`).
  - **Formal payment numbering (receipt number)** → defer M9 (payment receipt PDF needs sequential numbers); M7 payment use `id` + date identifier, don't occupy numbering sequence.
  - **Multi-currency payment / payment date exchange rate / exchange gain/loss (§7.4.5 cash basis)** → defer (same as M5/M6 single base currency). `payment.currency = base_currency`, `exchange_rate = 1`, `base_amount = amount`; non-base-currency amount backend reject.
  - **Online payment / bank flow auto reconciliation** → vNext (see roadmap §4.x).
  - **Payment receipt PDF / email** → M9.
- **Corresponding docs**: roadmap M7 / §2 (red lines **1 / 2 / 3 / 5 / 10**); analysis docs §2.3 / §2.4.2 / §2.5 / §7.4.5; M5 invoice implementation (`paid_status`/`due_amount`/`status`/`_ALLOWED_TRANSITIONS`).

## Pricing and State Rules (M7 fixed · `services/payment`)
> Completely tax-agnostic; schema only validates shape, all amount/state calculated by service. Engine is **pure function + one persist wrapper**: first implement pure recalculation (unit-testable), then service write result back to `invoice`.

- **Accumulate**: `paid_total = Σ payment.amount`; `base_paid_total = Σ payment.base_amount` (per-payment already 3 digits, sum no second rounding, D9).
- **Owed**: `due_amount = invoice.total_incl_vat − paid_total`; `base_due_amount = invoice.base_total_incl_vat − base_paid_total`. Overage guard guarantee `≥ 0`.
- **Payment status**: `due_amount == 0` → `PAID`; `paid_total == 0` → `UNPAID`; else → `PARTIALLY_PAID`.
- **Lifecycle (only engine-driven, D3)**:
  - `paid_status == PAID` and `status == SENT` ⇒ `status = COMPLETED`;
  - `paid_status != PAID` and `status == COMPLETED` ⇒ `status = SENT` (revert);
  - **never touch** `DRAFT` / `CANCELLED` (by D7 can't enter payment flow).
- **Overage guard (record/edit, D6)**: If operation makes `paid_total > invoice.total_incl_vat` → `422` (message: insufficient due amount to accommodate this payment).
- **Precondition guard (record/edit, D7)**: `invoice.status ∈ {SENT, COMPLETED}`, else `422` (message: issue invoice first before recording payment).
- **Single base currency (D2)**: `base_amount = amount`, `currency = invoice currency = company base currency`, `exchange_rate = 1`.

## Data Model / Migration
> UUID PK; root has `company_id` (red line 2); child FK cascade (red line 3); amount columns `NUMERIC`; text columns `text` (red line 10). **One additive migration**: build 1 table + indices; **don't touch `invoice` any columns** (`due_amount`/`paid_status`/`status` already in place). No new enums (reuse `InvoicePaidStatus`/`InvoiceStatus`).

- **`payment`**: `id`; `company_id` FK→`company.id` (`RESTRICT`) index; `invoice_id` FK→`invoice.id` (`CASCADE`) NOT NULL index; `payment_date` Date NOT NULL index; `amount` `NUMERIC(18,3)` NOT NULL; `base_amount` `NUMERIC(18,3)` NOT NULL; `currency` `String(3)` NOT NULL; `exchange_rate` `NUMERIC(18,8)` NOT NULL server_default `1`; `payment_method_id` FK→`payment_method.id` (`SET NULL`) nullable; `payment_method_name` text nullable (snapshot); `reference` text nullable; `note` text nullable; `creator_id` FK→`user.id` (`SET NULL`) nullable; timestamps. Indices `ix_payment_company_id` / `ix_payment_invoice_id` / `ix_payment_payment_date`.
- **Delete safety**: Delete `invoice` → DB cascade delete its `payment` (red line 3); delete `payment_method` → referencing payment `SET NULL` (preserve `payment_method_name` snapshot); delete `user` → `creator_id` `SET NULL`.
- **RLS**: Continue leave off; service layer centralizes `company_id` (red line 2).
