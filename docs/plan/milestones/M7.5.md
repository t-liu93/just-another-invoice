# M7.5 · 货币舍入口径修正（落到「分」/ currency minor unit）

> **状态**：设计/决策已与作者共定（2026-06-13），**未冻结、未实现**；进入时 JIT 补全原子步骤。排在 **M7 之后、M8 之前**（M8 开支也依赖本口径）。
>
> **缘起**：M7 收款人工 walkthrough 时发现真实发票 `F2026-009` 无法收满——含税总额存为 `3865.166`（3 位），UI 按 `toFixed(2)` 显示 `3865.17`，而收款只能按「分」（2 位）走，付 `3865.17` 量化成 `3865.170` > `3865.166` → 触发超额守卫；付 `3865.16` 余 `0.006`（显示 `0.01`），补 `0.01` 又超额。**根因不是浮点误差，而是 M5 定价引擎把「应付总额」也只量化到 3 位、从未落到货币最小单位（分）**，导致「显示 = 应付 = 对账」三者口径不一致。
>
> **上游**：红线 1（`docs/plan/roadmap.md` §2 —「金额一律 Decimal，舍入规则与位置定死」）；分析文档 §2.5（金额与精度）；M5 定价引擎（`services/pricing.py` / `services/money.py`）。

## 这一轮（M7）的处置（已定）
- **M7 本身不改舍入/引擎**，保持现状交付。收款的 sub-cent 边界（如 `F2026-009`）作为**已知遗留**顺延本里程碑。
- 作者的 M7 人工 walkthrough **不因该收款边界卡住**；其余 M7 功能（部分/多次收款、生命周期流转、概览、隔离等）业务形态 OK。
- M7 期间另有两处已批准的 walkthrough 小修（与本口径无关，单独收尾 commit）：① 概览页操作列列宽溢出；② 后端三条收款错误文案中文→英文。

## 目标
让**面向客户 / 对账 / 申报的货币量**统一落到**货币最小单位（v1 = EUR = 2 位 / 分）**，使「前端显示 = 应付额 = 后端对账 = 供应商发票 / 银行流水」自洽；同时**保留单价与中间计算的 ≥3 位精度**（你按 kWh/Wp 等单价计价的大件需要）。

## 已定决策（作者拍板 · 2026-06-13）
- **D1 · 舍入方法 = 方案 B（合计/分组级到分）**：每行每个产品**加完 VAT 后允许保留第 3 位**；在**汇总到面向客户的文档级金额**时再舍到 2 位。
  - JIT 待细化的子粒度：到分究竟在「**每个 VAT 税率组**的 taxable/VAT 各自到分后求和」还是「行保持 3 位、仅**最终文档总额**到分」。作者口述偏向「行可 3 位、最终报价/发票总额到 2 位」；实现时需与 **M10 BTW 按格子申报**口径对齐后钉死（每税率组的 VAT 申报数要能到分且自洽）。
- **D2 · 适用范围 = 全部「文档级」货币出参**：
  - **发票 invoice**：`total_incl_vat` / `due_amount` / 每 VAT 组 `taxable_amount`·`vat_total` / 对应 `base_*` 落到分。
  - **报价 quote / 估算对客面 estimate→quote 行**：发给客户的不含税价 / 含税合计落到分（estimate 内部成本/margin 可保留更高精度，客户面到分）。
  - **开支 expense（M8）**：每张 expense 的文档级净额/税额/含税额落到分（供应商发票的 VAT 本就到 2 位、银行流水也到 2 位，必须对得上）；中间 item 仍可 3 位。
- **D3 · 单价 / 中间计算保留 ≥3 位**：`unit_price`、行小计、折扣、逐行中间量不砍到 2 位，避免「单价 × 大数量」累计误差。
- **D4 · 不舍到整欧元**：VAT 必须按分计算与申报，引擎层**坚持到分**；若要「整数欧元的报价数字」，那是**报价输入/呈现**层的选择（输入端把单价/行价取整），不写进算钱引擎。
- **D5 · 不改列类型 / 不改 schema**：`NUMERIC(18,3)` 容得下 2 位（第 3 位恒 0）。引擎保证「文档级输出到分」即可，**无需 Alembic 改列**。
- **D6 · 引入 `currency_minor_unit` 概念**：v1 EUR 硬编码 = 2，留一个口子（未来某些币种 3/0 位）。集中在 `services/money.py`（如 `quantize_to_minor_unit(value, minor_unit=2)`），与既有 `quantize_money`（3 位中间精度）分工明确。
- **D7 · 历史数据重算（迁移）**：对已存的 3 位文档级金额（如 `F2026-009: 3865.166`）按 D1 口径**重算落库**；这步会变动历史 VAT/总额数字，实现时需用（生产库副本）核对一两张并经作者确认。重算后 M7 收款层**无需改动即自洽**（总额到分，收款到分，凑得平）。

## 范围边界
- **IN**：`services/pricing`（M5）+ `services/costing`（M6.5 对客面行）+ `services/expense`（M8，落地时对齐）的文档级到分；`services/money.py` 增最小单位量化工具；历史发票/报价重算脚本（一次性，幂等）。
- **OUT / 顺延**：多币种最小单位字典（v1 仅 EUR=2 硬编码 + 口子）；整欧元报价（输入层选择，不做引擎政策）；M7 收款引擎逻辑本身不改（其守卫/状态机在总额到分后自然成立）。

## 原子步骤（骨架 · 进入时 JIT 细化）
1. `services/money.py`：加 `MINOR_UNIT`/`quantize_to_minor_unit`（默认 2，ROUND_HALF_UP），单测覆盖（含 `3865.166 → 3865.17`、半分边界）。
2. `services/pricing.py`：在文档级汇总处把每 VAT 组 taxable/VAT + 单据 `total_incl_vat`/`due_amount` + `base_*` 落到分（口径 D1）；**算钱单测必更新**（红线 1），核对 excl+vat=total 在「分」精度自洽。
3. `services/costing.py`（M6.5 对客面）：estimate→quote 行的对客金额到分（内部成本/margin 精度不变）。
4. 历史数据重算脚本：幂等地把既有 invoice/quote 文档级金额按新口径重算落库；作者核对样本。
5. 回归：M5/M6/M6.5/M7 既有算钱与收款集成测试全绿；新增「3 位总额不可支付」回归用例（建发票使总额含第 3 位 → 重算后到分 → 可被「分」付款收满 COMPLETED）。
6. （M8 落地时）`services/expense` 文档级到分对齐同口径。

## 🟢 部署自测点（进入时补全 · 草案）
- 复现 `F2026-009` 同形态发票（单行单价 `3194.352`，21% VAT）→ 重算后含税总额落到分（`3865.17` 或按分组口径）→ 收款按显示金额能收满 → `PAID`/`COMPLETED`、`due=0`、无尾差。
- 多行多税率发票：每 VAT 组 VAT 到分、excl+vat=total 自洽；与一张供应商发票/银行流水金额对得上。
